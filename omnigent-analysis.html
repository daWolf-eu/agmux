Omnigent through an agmux lens

Omnigent is an open-source meta-harness: it wraps Claude Code, Codex, Cursor, Pi and SDK agents under one orchestration layer. agmux wants the opposite shape — provide the underlying mechanics, services and skills so those capabilities live inside the existing harnesses, with no harness built on top. This report extracts how omnigent solved the four shared problems and judges each mechanism for direct reuse.

General overview

Omnigent's core bet: never make the agent runtimes speak a new protocol. Instead, run the real CLI/SDK and normalize everything it does into one canonical event model and one tool/policy transport — observing and steering from outside.

Two stacked abstractions carry the whole design:

  • Layer A — Executor contract (omnigent/inner/executor.py:495). One abstract method run_turn(...) → AsyncIterator[ExecutorEvent] plus capability flags (supports_streaming, handles_tools_internally, supports_live_message_queue, interrupt_session…). Every backend is forced to yield the same event vocabulary: TextChunk, ReasoningChunk, ToolCallRequest, ToolCallComplete, TurnComplete(usage), ExecutorError.
  • Layer B — harness wrap. Each harness is a thin subprocess exporting a FastAPI create_app(), registered in _HARNESS_MODULES (omnigent/runtime/harnesses/__init__.py:34) and served over a Unix socket by HarnessProcessManager.

The single most important distinction in the codebase

native  Native CLI/TUI bridges — claude-native, codex-native, pi-native.
Omnigent does not run the model. The real claude/codex binary runs in a tmux pane (or app-server). Omnigent observes from the outside (hooks, file tailing, app-server RPC) and injects input (tmux send-keys / RPC). All capability is added via the CLI's own extension points.

sdk  In-process SDK harnesses — claude-sdk, codex, cursor, pi, openai-agents, antigravity.
Omnigent is the agent loop driver. It imports the vendor SDK, registers tools as the SDK's native type, and enforces policy via SDK callbacks (can_use_tool). Events come back lossless and real-time.

Why this matters for agmux: agmux lives inside harnesses (tmux panes / installed CLIs). That maps almost entirely onto omnigent's native path — the extension-point injection and outside-in observation. The sdk path and the FastAPI subprocess machinery are meta-harness scaffolding agmux does not need.

Reuse for agmux The hook-as-instrumentation pattern is the highest-leverage idea — it is "monitoring within the existing harness," zero CLI changes. Also lift: the fast/slow channel split (high-freq text → append file; rare decisions → long-poll), the small session_stream.py (~150 LoC) + inflight_text.py pub-sub/replay core, and the cost dual-tracking insight (the CLI's reported cost lags real spend, so keep a separate estimate for gating).
Skip / over-engineered The polling forwarder + durable-cursor machinery exists only because omnigent observes from outside; if agmux instruments from within (hooks emit straight to a local collector) the entire tail-and-reconcile layer disappears. Also skip the runner↔server WS tunnel + SSE relay + central DB (NAT/multi-tenant SaaS scope) and the MLflow tracing backend (local OTel spans are the reusable kernel).

QUESTION 2How omnigent steers other harnesses & injects prompts

Input and output are asymmetric: input goes in via send-keys / injection-queue / RPC; output comes back via the file-tailing forwarder. For native CLIs, the harness's run_turn returns immediately after the paste lands — the turn is observed, not awaited.

End-to-end flow — browser message → running claude-native pane

Approval / elicitation / interrupt model

Policy actions are exactly {ALLOW, ASK, DENY} (spec/types.py:1071) — there is no ESCALATE. Four distinct, mostly in-memory concepts:

  • Approval (runner/pending_approvals.py): dict[str, Future[bool]] keyed by elicitation_id; verdict arrives as an approval event → set_result → parked coroutine resumes and retries the tool.
  • Server-side park (server/_elicitation_registry.py): races the Future against "answered in the native TUI" and a disconnect poller — whichever resolves first wins.
  • Elicitation index (runtime/pending_elicitations.py): a UI badge index, not a park.
  • Interrupt: dispatched per-harness — claude = Escape, codex = turn/interrupt RPC, pi = abort(), SDK = cancel the turn task (runner/app.py:10013).

Supervisor → sub-agent delegation (the Polly pattern)

Delegation is session-based, not in-context. A parent spawns a child Omnigent conversation and drives it via one merged tool, sys_session_send (tools/builtins/spawn.py:56):

  • Named mode (agent, title): first call creates+starts the child; same pair later continues it (full history + new args) — this is how a parent re-steers a running child.
  • Dispatch is always async, returning {task_id, conversation_id, status}; parallel fan-out = multiple calls in one response. Child runs autonomously; the runner drops the result on the parent's inbox and posts a wake notice; parent collects via sys_read_inbox.
  • Blocked-child escalation: SubagentBlockNotifier (runtime/subagent_block_notifier.py:97) watches for a child blocked on a human approval, waits a 120s grace, then wakes the parent.
Reuse for agmux agmux already lives in tmux, so the prize is concentrated in ~140 lines of inject_user_message / inject_interrupt / kill_session. Lift specifically: bracketed-paste-via-file-buffer (the fix for the 16KB cap & per-newline submit bug), verified submit (poll-Enter-repoll — don't skip it), prompt-glyph readiness gating, and the clean Escape=soft / kill=hard split. Session-based sub-agent delegation maps naturally onto agmux panes — each child is its own pane, the parent steers by re-sending — far simpler than in-context sub-agents, and cross-vendor mixing comes free.
Skip / simplify Nearly all remaining complexity exists because omnigent is a remote, multi-user, multi-host meta-harness: the filesystem rendezvous (tmux.json/bridge.json), the runner↔server WS tunnel, persist-vs-bypass dispatch, dual Future-park registries, access levels, and injection_id exactly-once correlation. agmux owns its panes directly (no rendezvous needed) and is single-user-local. For pure-tmux agmux, every harness is a "native" pane, so the send-keys path is the only path — no scaffold injection queue, no continuation drain.

QUESTION 3How omnigent shares data & artefacts between harnesses

Two persistence axes — metadata stores (SQL) + a blob store — tied by a shared opaque id, plus an ephemeral in-memory event bus. The standout cross-harness primitive is the file_id → data: URI resolver.

The load-bearing design point: the metadata/blob split. FileStore.create() returns a file_id; ArtifactStore.put(stored.id, bytes) stores bytes under that same id. Read reverses it. No FK gymnastics.

How an artefact becomes visible to any harness

content_resolver.resolve_content_references (runtime/content_resolver.py:251) rewrites a {file_id} block → file_store.get (ownership) → artifact_store.get → base64.b64encode → inline data: URI (image_url / file_data), per-turn cache ⇒ provider-agnostic: a file produced under harness A is injected inline into harness B's next message

Git worktree strategy (Polly)

Parallel coding sub-agents are isolated in sibling git worktrees, each on its own branch; only diffs cross to reviewers — never filesystem access.

  • create_worktree() runs git worktree add -b <branch> <path>, always resolving to the main repo root so worktrees are siblings, never nested (host/git_worktree.py:275). Each child's workspace becomes its terminal cwd.
  • Polly extracts git diff main...HEAD (or gh pr diff) and dispatches it to a different-vendor reviewer that receives only the diff text. Sharing is diff-as-message, not shared FS.
  • Cleanup: git worktree remove --force + git branch -D.

Cross-device sync & sandbox filesystem

Sync (terminal / browser / phone)

Durable ordered log + ephemeral fan-out, reconciled client-side by id dedup. Deliberately no replay machinery: SQL position-ordered log is the cursor; SSE fan-out is live-only; reconnect = open SSE + GET snapshot + dedupe by stable item id.

Sandbox (Modal / Daytona / Islo)

No mounted volumes. All FS access is per-operation RPC: OSEnvironment ABC (read/write/edit/shell). Remote sandboxes run the same runner; the server reaches it through an HTTP-over-WebSocket tunnel, base64-streaming bodies back.

Reuse for agmux Steal the metadata/blob split (clean, FK-free) and especially the file_id → data: URI resolver — it is the single most reusable idea for "artefact from harness A visible to harness B," provider-agnostic by design. git_worktree.py is almost lift-and-ship (sibling resolution, branch validation, create/remove). Adopt diff-as-message reviews and the snapshot+dedup-by-id reconnect contract (far simpler than event-sourced replay). Keep the download hardening (Content-Disposition: attachment + nosniff) — serving harness-produced files to a browser inherits the exact stored-XSS risk.
Skip / simplify Drop the WS HTTP tunnel and per-op OSEnvironment RPC unless agmux must itself drive remote sandboxes — if harnesses own their sandboxes, agmux only needs metadata+blob+resolver and lets harnesses push artefacts in. The in-process session_stream won't survive multi-process: for independent harnesses you'd back the same publish/subscribe interface with Redis pub/sub or Postgres LISTEN/NOTIFY. Collapse comment/policy/permission/agent stores you don't need.

QUESTION 4 · most important for agmuxHow omnigent adds its functionality to every harness

This is the heart of the matter and where agmux and omnigent overlap most. The answer for the native path is exactly "mechanics within the harness": MCP server injection for tools, a shared command-hook bridge for policy/monitoring, skill bundling via the plugin convention, and local proxies for credentials/gateway — all via the CLI's own documented extension points, with no file written into the user's real config.

The common injection primitives

  1. Stdio MCP server as the universal tool transport. Both native harnesses inject the same module — python -I -m omnigent.claude_native_bridge serve-mcp --bridge-dir <d> — differing only in config format (Claude: --mcp-config JSON; Codex: [mcp_servers.omnigent] TOML). It advertises the sys_* tools and relays calls back to the active turn.
  2. Shared command-hook policy bridge (omnigent/native_policy_hook.py). Claude Code and Codex emit identically-shaped hook payloads, so one harness-neutral translator serves both: hook_payload_to_evaluation_request maps PreToolUse→PHASE_TOOL_CALL, PostToolUse→PHASE_TOOL_RESULT, UserPromptSubmit→PHASE_REQUEST; evaluation_response_to_hook_output maps verdicts back. PreToolUse fails closed on server outage; result phases fail open.
  3. Skill bundling (omnigent/inner/bundle_skills.py). Materializes skills/<name>/SKILL.md, writes .claude-plugin/plugin.json, and translates a skills_filter into --plugin-dir / --setting-sources "" CLI args. Pure Claude Code plugin convention — no orchestration needed.
  4. Credential proxy & gateway shim. credential_proxy.py keeps real secrets in the parent and swaps them in at an egress MITM proxy per-host (with oa_cred_* placeholders + a cross-host 403 leak guard). claude_gateway_shim.py is a localhost reverse proxy (pointed at via ANTHROPIC_BASE_URL) that patches request bodies the Claude CLI mis-builds for non-Anthropic gateways.

Claude Code specifically — the extension points used (all via inline flags, nothing written to ~/.claude/settings.json)

  • --mcp-config <json> → the tool transport (single stdio server).
  • --settings <json> → hooks for SessionStart/Stop/StopFailure/UserPromptSubmit/PreToolUse/PostToolUse/PreCompact/MessageDisplay/PermissionRequest/TaskCreated/Completed, plus a chainable custom statusLine and apiKeyHelper.
  • --plugin-dir + --setting-sources → skills via the plugin convention.
  • Transcript mirroring by persisted byte offset; workspace pre-trust seeds ~/.claude.json to skip onboarding hangs. Notably no --append-system-prompt — the native terminal owns its prompt.

Codex specifically

Uses the codex app-server JSON-RPC protocol, not keystrokes. Injection writes into a private per-session CODEX_HOME (never the user's real config): [mcp_servers.omnigent] appended to config.toml, hooks.json registered, model pinned. Hooks require codex ≥0.129 and must be explicitly trusted via the same hooks/list→config/batchWrite flow the TUI uses, or they're silently skipped.

Reuse for agmux — the reusable core is items 1–3 (1) The shared command-hook bridge (native_policy_hook.py) is the single most reusable file — pure stdin→JSON→HTTP→stdout, harness-agnostic because Claude and Codex emit identical payloads. Ship a hook script + a settings/hooks writer and you get policy/monitoring into any CLI with a hook system, no meta-harness. Copy the fail-closed/fail-open phase semantics verbatim. (2) MCP server injection (write [mcp_servers.X] / --mcp-config) is exactly how agmux exposes its services as tools inside the harness — and copy the symlink-materialization care so the user's real config is never edited. (3) Skill bundling (plugin.json + --plugin-dir) is directly portable. The credential/gateway proxies are standalone localhost proxies, reusable for secret injection / request fixups.
Tied to the meta-harness — not reusable The Executor/ExecutorEvent abstraction + _HARNESS_MODULES/ExecutorAdapter FastAPI-subprocess machinery exists to normalize backends so omnigent can drive them — agmux, living inside the harness, never re-implements a runtime's loop. The SDK in-process integrations (create_sdk_mcp_server, can_use_tool, cursor custom_tools) require owning the process and importing the vendor SDK; agmux must use the external extension points instead. ProxyMcpManager central policy routing assumes a server holding session state — agmux enforces locally in the injected hook/MCP server.
Concrete recommendation agmux's reusable kernel = a per-harness config writer (settings.json hooks + MCP config + plugin dir) + a shared stdin/stdout hook bridge + a stdio MCP server. Reuse omnigent's native_policy_hook.py translation table and bundle_skills.py almost verbatim; reimplement enforcement to be local rather than routed through a server.

Other interesting findings (agmux-relevant)

The repo dogfoods skills for its own development

.claude/skills/cursor-sdk-e2e-dev and antigravity-sdk-e2e-dev are SKILL.md files used to develop the harness adapters themselves. Confirms the maintainers treat skills as a first-class extension surface — the same lever agmux wants to offer.

Cross-vendor review is a product principle, not a feature

Polly mandates that a diff written by one vendor is reviewed by a different vendor (claude-native code → codex reviewer, etc.). Mechanically free because delegation is session-based and harness-agnostic. A strong validation of agmux's multi-harness premise: heterogeneity is an asset when the substrate normalizes it.

Fail-closed vs fail-open is phase-specific, and deliberate

PreToolUse fails closed (deny on server outage) — you must not let an unreviewed dangerous tool run. PostToolUse/UserPromptSubmit fail open — blocking after the fact or on prompt submit only harms UX. A small, well-reasoned safety stance worth copying exactly.

Two costs, because the CLI's number lies

Claude's /cost statusLine lags real spend (especially with sub-agents), so omnigent gates budgets on max(statusLine, transcript-estimate) while still displaying the verbatim CLI value. If agmux ever enforces spend caps over a wrapped CLI, this gotcha is non-obvious and load-bearing.

Versioned protocol fragility & trust gating

Codex hook enforcement silently disables below v0.129 and requires an explicit trust handshake. Practical reminder: in-harness instrumentation rides on the host CLI's evolving extension API — agmux needs version detection and graceful, surfaced degradation, not silent failure.

The hard-won tmux details are the real IP

Bracketed-paste-via-file-buffer (16KB cap + per-newline submit bug, referencing anthropics/claude-code#52126), verified-submit polling, and prompt-glyph readiness gating are the kind of fixes only found by hitting the bugs in production. For agmux these ~140 lines are worth more than the entire surrounding architecture.

Synthesis — what agmux takes, what it leaves

Omnigent and agmux share the same four problems but invert the topology. Omnigent drives harnesses from a central server; agmux augments harnesses from inside. Almost everything omnigent built for the native path transfers; almost everything built for being a remote multi-tenant orchestrator does not.

The one-paragraph thesis Omnigent has already proven that Claude Code and Codex can be fully instrumented and tool-extended through their own published extension points — hooks, MCP config, plugin/skill dirs, gateway env — with zero modification to the CLIs and (for native) without driving the agent loop at all. That proof is exactly agmux's design space. agmux should harvest the four self-contained primitives (hook bridge, MCP/config injection, skill bundling, tmux steering) and the small event/replay core, then build them as local services rather than as clients of a central orchestrator — discarding the Executor normalization layer, the runner/server tunnel, and the multi-tenant persistence that only exist because omnigent chose to be the harness on top.
